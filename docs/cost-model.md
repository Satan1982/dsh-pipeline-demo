# 成本模型（实测 + 估算，2026-10-26）

原则：**能测的写实测，不能测的标「估算」并写出公式**，不拿感觉当数字。

## 1. 实测：语义评审团（唯一每单必跑、又完全不产生代码的付费调用）

用仓库里真实 diff（`HEAD~1`，1 个文件）跑一次评审团，从 API 的 `usage` 字段拿到原始数字：

| 评审器 | prompt | completion | total |
| --- | --- | --- | --- |
| `Qwen/Qwen3.5-122B-A10B` | 1,302 | 5,743 | 7,045 |
| `moonshotai/Kimi-K2.7-Code` | 1,206 | 863 | 2,069 |
| **合计** | 2,508 | 6,606 | **9,114** |

- 耗时：并行，约 15 秒（单模型时期 51–61 秒，并行反而更快）。
- 这个数字已经接进代码：`ci/semantic-review.mjs` 返回 `tokens`，日志里显示 `评审团 2/2 有效（… tokens=9114）`。
- 规模：diff 越大 prompt 越大；Qwen 的 5.7k completion 主要花在「逐条核对验收」的推理上，属正常。

**按 diff 规模估**：1 文件 ≈ 9k tokens；5 文件 ≈ 25k–40k tokens（实测 #64/#61 的 PR 在这一档）。
按国产 API 常见价位（输入 ¥1–4/M、输出 ¥4–16/M）算：**单次评审 ≈ ¥0.02–0.15**。

## 3. 实测：agent 侧（写代码的那部分）

**这一层目前无法在本地计量**：`dsh headless` 不输出 `usage`，`~/.dsh/sessions/*.zstd` 里
77 个 worktree 会话全部没有 token 字段（已逐个解压扫过，0 命中）。

可用的替代口径：

| 口径 | 实测值 |
| --- | --- |
| 单次 headless 时长 | 40–90 秒（29B 成功案例），213–522 秒（strong 解复杂冲突/大改） |
| 一单的 agent 调用次数 | 1–3 次（`DSH_MAX_ATTEMPTS`，失败才重试） |
| 失败率 | 探针期较高（#48/#49 三次全败），门禁收紧后正常单次即过 |

**估算公式**（不是实测，请自行替换单价与吞吐）：

```
单次 agent 成本 ≈ (输入 token × 输入单价) + (输出 token × 输出单价)
输入 token ≈ 仓库上下文 + PLAN.md + 已有代码，按 20k–60k 估
输出 token ≈ 改动量（patch）≈ 1k–8k
```

按硅基流动上 DeepSeek-V4.1-Flash 一类的价位（输入约 ¥1/M、输出约 ¥4/M）：
**一单正常完成 ≈ ¥0.03–0.10；三次重试 ≈ ¥0.1–0.3**。

## 5. 结论与可优化项

1. **评审团不是成本大头**（每单几分钱到一毛），不值得为了省钱退回单模型——它挡住过一次真实越界
   （`.dsh/PLAN.md` 被 `git add -f` 提交进 PR）。
2. **真正的成本是「失败重试」**：一单失败 3 次 = 3 倍 agent 调用 + 3 倍评审。已做的杠杆是
   重试第 2 次自动升级 strong（少走弯路）、失败指纹回灌（避免同错）。
3. **缺的是计量**：要让成本可控，第一步是让 agent 侧吐 usage。可做的三条：
   - headless 输出带上 provider 的 `usage`（需要 DSH 侧支持）；
   - 用 provider 后台账单按日对账；
   - 在 dispatch 里记录每单的「attempt 数 × 时长」，作为代理指标（已写进日志）。
