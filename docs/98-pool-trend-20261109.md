# 池子健康趋势进 distill（2026-11-09）

## 为什么

`ci/dispatch.mjs --pool-snapshot` 每小时往 `~/.dsh/coord/log/pool-snapshot.jsonl` 追加一行，
但这份数据一直没人读：池子从 10-28 的 102 ok 一路掉到 11-02 之后的中位 17.5–20，
流水线全程没有信号——**只有任务开始失败，才会反过来暴露池子坏了**。
`docs/dispatch.md` 里记着这条 TODO：「还没接进每日 digest（`ci/distill-failures.mjs` 里读最近 N 行出曲线）」。

## 做了什么

- 新增 `ci/pool-trend.mjs`：解析 JSONL、按天聚合、渲染一段统计；纯读，不探活、不读远端、不改登记表。
- `ci/distill-failures.mjs`：失败摘要与池子统计**分两次投递**——失败指纹 → `pipeline::failures`（默认，
  `--bank`/`DSH_HINDSIGHT_BANK` 可改），池子统计 → `pipeline::pool`（`--pool-bank`/`DSH_POOL_BANK` 可改）。
  池子段写进 failures bank 会被检索成「当前可用性」，所以拆开。
- `ci/dispatch.mjs`：常驻循环里把 `maybePoolSnapshot()` 挪到 `maybeDistill()` 之前，否则 07:00 的蒸馏
  读的是上一小时的快照。
- `docs/dispatch.md`：TODO 换成现行口径。

## 口径（为什么不是「首尾差」）

初版按「窗口首尾 ok 之差 ±5」判方向，三次独立审核里两次实测否掉了它：

- 快照会断档：162 行覆盖约 12 天，行间隔中位 1.01h 但有一个 77.5h 的空洞；「48 行」在历史上
  中位对应 110.5h，最长 201.6h——**行数不等于时间**。
- ok 数有强烈日内相位：按 UTC 小时统计 mean 在 27–95 之间摆动，11-08 22:58Z 是 11、23:58Z 是 86；
  同一份数据换窗口长度（12/24/72/120/162 行），方向会 flat/-42/+5/+3/-12 乱跳。07:00 蒸馏正好踩在
  相位翻转点上，报出的「回升」很可能是取样时刻的假象。
- 每日尖峰 ~97（10-29、11-03、11-07/08/09）是心跳刷新造成的，首尾差会被它带偏。

现在的口径：

- **时间窗 14 天**（`DSH_POOL_SNAPSHOT_DAYS` 可调，上限 90），锚在最新一条快照，不按行数。
- **按 UTC 日聚合**：每日中位 ok + 当日 min–max + 次数，摆出整条序列。
- 只报「较窗口首日的中位变化」这个数字，**不下结论**：不写「⚠ 池子在变差」，也不替人判断当前可用性。
- 坏行计数并写明「跳过 N 行无法解析」；文件读不了（是目录 / 权限）与全坏行都报 `problem`，不再静默当成没数据。

## 边界

- 只让「池子在变差」出现在每日摘要与 Hindsight 里；**不自动探活、不自动换模型、不动登记表**——那仍是
  `fm.py` 与心跳/探针任务的职责。
- 统计说的是历史，不是可用性：要看逐行去 `tail ~/.dsh/coord/log/pool-snapshot.jsonl`。
- `ci/` 是受保护目录：提交按仓库约定 `git commit --no-verify`（`AGENTS.md` 第 61 行）；
  推 main 走 `DSH_LAND_GATE_UPDATE=1` + 理由并留痕 `.logs/gate-update-overrides.jsonl`（2026-11-09 经用户授权），
  落地后 GitHub `verify` check 绿、Gitee 镜像由 `DSH_GITEE_ALLOW_UNVERIFIED=1` 放行。
